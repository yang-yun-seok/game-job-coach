# 직무 선택과 공통 평가 기준

이 문서는 세부 직무에 맞는 근거를 찾기 위한 코칭 기준이다. 회사의 공식 채점표나 합격 기준이 아니며, 실제 공고와 사용자가 요청한 범위를 우선한다.

## 직무를 먼저 선택한다

1. 공고의 **담당 업무·산출물·책임 범위·협업 상대**에서 주된 직무와 필요한 인접 직무를 찾는다. 직함, 사용 툴, 회사가 게임사라는 사실만으로 분류하지 않는다.
2. `주된 직무 / 함께 볼 세부 업무 / 근거가 된 공고 항목 / 불확실한 범위`를 간단히 정리한다. 이미 명확하면 별도 분류표를 출력하지 않아도 된다. 공고가 없으면 사용자가 밝힌 목표와 작업물 범위로 잠정 선택한다.
3. 아래에서 해당 파일과 관련 절만 읽고 요청한 모드에 적용한다. 복합 직무는 실제 업무별로 기준을 함께 사용하되, 인접 직무의 기준을 전부 필수 요건으로 가져오지 않는다.
4. 분류에 따라 결과가 크게 달라지면 핵심 업무를 한 번 확인한다. 그동안 공고의 명시 요건 대조 등 독립적으로 가능한 작업은 진행한다. 확인 전에는 가능한 해석을 나눠 제시한다.

직군 체계를 모든 회사에 공통된 정답으로 취급하지 않는다. 목록에 없거나 새로운 직무라면 공고에서 요구한 업무와 결과물을 기준으로 잠정 평가 항목을 만들고, 적용 범위와 확인 필요 사항을 밝힌다. 억지로 가장 가까운 직군에 끼워 맞추지 않는다.

## 게임업계 맥락에 맞추기

- **프로젝트·서비스 단계**: 공고에서 확인한 신규 개발·프로토타입·출시 준비·라이브 서비스 단계에 맞춰 본다. 새 기능 제작과 기존 콘텐츠 유지·패치·장애 대응을 같은 경험으로 바꾸지 않는다. 단계가 없으면 추정 대신 미확인으로 둔다.
- **게임과 플레이 이해**: 장르·코어 루프·전투·성장·과금·커뮤니티 중 실제 업무에 관련된 이해를 확인한다. 특정 게임 플레이 시간·진행도·장르 경험이 명시 요건이면 그대로 대조한다. 모든 직군에 일괄 요구하지 않되, 명시 요건을 일반론으로 완화하지도 않는다. 플레이했다는 사실과 설계·운영 의도를 설명하는 능력은 구분한다.
- **플랫폼·지역·서비스 형태**: PC·모바일·콘솔, 입력·화면·성능 제약, 언어·지역, 싱글/온라인 등 확인된 조건에서 해당 직무에 미치는 차이를 읽는다. 모바일 UA 기준을 PC 패키지 마케팅 전체의 기준으로 쓰거나, 한국 서비스 경험을 모든 지역 운영 경험으로 바꾸지 않는다.
- **제작과 적용 과정**: 기획 문서·데이터테이블·엔진/에디터 적용·아트/오디오 자산·빌드·검수·패치 사이에서 맡은 산출물과 전달·수정 범위를 확인한다. 문서 작성, 실제 제작·적용, 라이브 운영을 구분하고, 공고가 요구한 도구·적용 업무를 문서 설명만으로 충족했다고 하지 않는다.
- **개발사·퍼블리셔·협력사 역할**: 실제 팀의 제작·사업·운영·납품 책임과 승인 관계를 본다. 회사 유형만으로 역할을 확정하지 않고 공고와 경험에 명시된 협업 경계를 따른다.
- **현재 공고로 보정**: 아래 참고 공고는 기준을 점검한 사례다. 새 지원 건에서는 해당 공고의 최신 본문을 우선한다. 본문을 읽지 못했다면 제목·검색 요약으로 세부 업무나 제출 조건을 확정하지 않는다. 업계 관행이라는 주장을 새로 덧붙일 때도 확인한 출처와 적용 범위를 밝힌다.

## 이름이 겹치는 직무의 경계

- **PM**: 일정·의존성·제작 위험 관리인지, 제품·사업 성과와 우선순위 판단인지, 현지화 납품 관리인지 실제 책임을 본다. 한 사람이 여러 역할을 맡으면 각각의 근거를 구분한다.
- **UI·UX**: 플레이 과제와 화면 흐름은 기획, 시각 언어·그래픽 제작은 아트, 조사 설계·사용자 관찰은 리서치 기준을 선택한다.
- **TA·렌더링·VFX**: 제작 도구·파이프라인 연결, 렌더링 시스템 구현, 효과의 시각 표현 중 맡은 일을 구분한다. 셰이더 사용만으로 세 역할을 동일하게 평가하지 않는다.
- **QA·LQA·CS·커뮤니티**: 기능 검증, 언어·문화·문맥 검증, 개별 문의 해결, 이용자 집단과의 소통·운영을 구분한다. 이슈 전달 같은 공통 업무도 목적과 결과물에 맞춰 읽는다.
- **데이터·라이브·사업**: 데이터 수집 체계, 분석·실험, 콘텐츠 규칙, 사업적 의사결정 중 책임진 부분을 확인한다. 같은 매출 지표를 썼다고 같은 직무로 분류하지 않는다.
- **사운드**: 음원의 제작 품질과 엔진 내 상호작용·자원 관리를 구분한다. 작곡가에게 테크니컬 오디오 전체 역량을 일괄 요구하지 않는다.

## 근거의 깊이와 지원 요건을 구분한다

| 확인 수준 | 읽을 수 있는 근거 | 다음 확인 |
|---|---|---|
| 주장·결과물 소개 | 역할·도구·성과 진술, 결과물 존재 | 본인 범위와 구체적 사례 |
| 판단·과정 | 목표·제약, 대안과 선택 이유, 실제 수행 과정 | 결과와 확인 방법 |
| 검증·수정 | 조건·관찰 결과·한계, 수정과 재확인 | 공고 업무에 적용 가능한 범위 |

이는 근거 설명의 깊이이며 경력 등급·합격 점수·요건 충족률이 아니다. 요건 충족 여부는 [서류 진단](document-review.md)의 상태 기준을 따로 적용한다. 예를 들어 학습 작업의 검증이 충실해도 명시된 상용 운영 경력이 생기지는 않는다.

- **신입·전환 지원자**: 개인·학교·동아리·공개 자료·가상 데이터 작업은 그 범위의 판단 근거가 될 수 있다. 공고에 없는 출시·대규모 트래픽·광고 집행·상용 납품 경험을 공통 필수로 만들지 않는다. 다른 업계의 경험은 옮겨 쓸 수 있는 역량과 게임업무에서 추가 확인할 차이를 분리한다.
- **경력 지원자**: 본인 결정·기여, 실제 적용 범위, 운영·납품·유지보수 결과와 한계를 확인한다. 자료 미제공을 경험 부재로 단정하지 않는다.
- **리드·관리 역할**: 공고에 책임이 명시된 경우에만 우선순위·위임·검토·육성·이해관계자 조율 근거를 추가한다. 근속 연수만으로 리더십이나 채용 권한을 가정하지 않는다.
- **작업물 확인**: 코드·이미지·영상·음원·실행 결과를 보지 못했다면 품질을 직접 확인했다고 말하지 않는다. 설명의 구체성과 직접 관찰한 품질을 분리한다. 자료 형식과 제출 요구는 공고에 맞추며 모든 직무에 게임 제작 포트폴리오를 요구하지 않는다.
- **기밀·성과**: 회사 원본이나 고객·직원 정보를 요구하지 않는다. 공개 가능한 요약·익명화 사례·가상 재현을 활용하고 검증 범위를 밝힌다. 수치는 기간·대상·분모·비교 조건·개인 기여를 확인하고 상관관계를 인과 성과로 부풀리지 않는다.

## 각 모드에 적용

공고 분석에서는 맡길 일과 확인할 신호를, 서류에서는 실제 근거와 부족한 연결을, 자소서에서는 해당 직무의 판단을 보여 주는 장면을, 면접에서는 그 판단을 확인할 질문을 고른다. 준비 계획의 보완 과제도 같은 직무의 산출물과 완료 기준을 사용한다. 직군 목록을 나열하는 것으로 적용을 대신하지 않는다.

직군 범위는 [Ubisoft의 직무 안내](https://www.ubisoft.com/en-us/company/careers/our-jobs), [Blizzard의 직군 안내](https://careers.blizzard.com/global/en/disciplines), [Riot Games의 채용 목록](https://www.riotgames.com/en/work-with-us/jobs)을 참고해 점검했다. 세부 평가 문항은 이 스킬의 코칭 제안이며 해당 회사의 공식 심사 기준이 아니다.
