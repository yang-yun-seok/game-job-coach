# 직무별 근거를 읽는 관점

아래는 코칭용 관찰 기준이며 업계 공통 채용컷이나 회사의 공식 평가표가 아니다. 해당 공고의 업무·필수·우대, 세부 직무, 경력 수준을 먼저 확인하고 관련된 행만 사용한다. 표의 판단 예시는 가상이며 지원자에게 관찰된 사실처럼 쓰지 않는다.

## 적용 방식과 근거의 깊이

각 판단을 `자료 위치 → 실제로 관찰한 내용 → 설명 가능한 역량과 남은 한계 → 다음 행동`으로 연결한다. 근거의 깊이는 다음처럼 읽되 점수나 합격 단계로 바꾸지 않는다.

| 근거의 깊이 | 관찰할 내용 | 해석의 한계 |
|---|---|---|
| 진술·요약 | 사용 툴, 담당 업무, 결과를 설명한 문장 | 경험 진술로 인정하되 선택 과정·품질까지 확인한 것은 아님 |
| 설계·선택의 근거 | 규칙·산출물과 목표·제약·대안·본인 결정의 연결 | 설계 판단을 설명할 수 있어도 구현·운영 성과는 별도 확인 |
| 검증·수정의 근거 | 조건과 방법이 있는 테스트, 관찰 결과, 변경 전후와 한계 | 확인한 조건 안의 결과이며 상용 환경·다른 이용자까지 일반화하지 않음 |

근거의 깊이와 [공고 충족 상태](document-review.md)는 별개다. 구체적인 학습용 밸런스 시뮬레이션은 설계·검증의 근거가 될 수 있지만 ‘상용 라이브 운영 경험’ 요건의 증거로 바꾸지 않는다. 반대로 명시 요건이 단순 도구 사용 경험이라면 상세 검증 기록이 없다는 이유만으로 미충족 처리하지 않는다.

신입의 학습·역기획·개인 프로젝트는 목표 설정, 판단, 검증 가능한 범위와 학습을 본다. 경력은 공고가 요구하는 책임 범위·협업·결과와 대조한다. 신입에게 매출·상용 운영 성과를 일괄 요구하거나 경력에게도 공고에 없는 규모·성과를 추가하지 않는다. 실제 관찰, 설계 가정, 검증 계획, 실행한 검증을 구분한다.

## 게임기획 공통

| 관찰할 증거 | 판단 예시 | 다음 보완 행동 |
|---|---|---|
| 대상 유저·플레이 상황, 해결할 문제, 목표와 제약 | ‘재미를 높인다’만 있으면 의도는 보이나 성공 조건은 확인하기 어려움 | 도입부에 바꾸려는 플레이 행동과 확인 방법을 적고 가정은 표시 |
| 입력·조건·상태 변화·결과, 데이터 필드, 오류·예외 처리 | 정상 흐름만 있으면 핵심 규칙은 확인되나 중복 요청·중단 시 동작은 불명확 | 관련 페이지에 주요 예외와 우선순위, 필요한 데이터 정의 추가 |
| 본인 결정과 타 직군 전달 사항, 변경 이유와 영향 | 완성 문서만으로 본인 설계 범위나 협업 과정을 확정할 수 없음 | 담당 범위와 실제 주고받은 쟁점·결정 한 사례를 기존 경험에서 보충 |
| 목표와 연결된 테스트 조건·결과·수정 | ‘피드백을 반영했다’는 문장만으로 무엇이 개선됐는지 확인 불가 | 관찰한 문제, 바꾼 규칙, 재확인 결과를 연결; 미실행이면 계획으로 표시 |

## 시스템·경제 기획

| 관찰할 증거 | 판단 예시 | 다음 보완 행동 |
|---|---|---|
| 핵심 행동→보상→성장→새 선택의 루프, 해금·정체 구간 | 기능 목록은 범위를 보여주지만 기능이 플레이를 이어주는 이유는 약함 | 핵심 루프 한 장에 기능별 역할과 성장 병목을 연결 |
| 재화별 수급·소모처, 지급 주기·상한, 유저 유형·기간별 잔액 | 가격표만으로 인플레이션 통제나 보상 적정성을 판단할 수 없음 | 가정을 공개한 수급·소모 표와 대표 플레이 패턴의 잔액 추이 추가 |
| 성장식·확률·보상 수치의 단위·변수·선택 이유, 대안 비교 | 계산식이 있어도 입력 가정이 없으면 결과를 재현하기 어려움 | 입력값·단위·대표 구간을 밝히고 핵심 변수 변화 시 결과 비교 |
| 반복 수령·초과 보유·중도 이탈 등의 처리, 수치 검증 | 시뮬레이션상 목표 달성은 해당 가정의 결과이며 실제 유저 반응은 미확인 | 극단 입력·악용 가능성의 확인 사례를 보충하고 플레이 검증을 별도 제안 |

## 콘텐츠·레벨 기획

| 관찰할 증거 | 판단 예시 | 다음 보완 행동 |
|---|---|---|
| 학습·도전·숙련 목표와 구간별 과제, 난도·휴식의 배치 | 맵이 크거나 콘텐츠가 많다는 사실만으로 페이싱의 적절성은 설명 안 됨 | 구간별 목표·예상 행동·실패 원인·회복 구간을 동선에 표시 |
| 실제 확인한 맵·블록아웃의 시야·경로·유도·위험/보상 배치 | 복수 경로가 있어도 선택 기준과 돌아오는 구조가 없으면 의도 확인이 어려움 | 주요 분기마다 유저가 읽을 단서와 선택의 비용·보상을 명시 |
| 재플레이 변주, 콘텐츠 생성·확장 규칙, 제작 제약 | 개별 스테이지 완성만으로 확장 가능한 제작 체계를 입증하지 못함 | 공고에 필요할 때 재사용 규칙·예외와 추가 콘텐츠 예시를 작성 |
| 플레이 관찰·이탈/실패 지점, 변경 전후 배치와 재시험 | 소수 지인의 테스트도 관찰 근거가 되지만 전체 유저를 대표하지 않음 | 테스트 대상·조건·관찰과 해석을 구분하고 가장 큰 문제의 수정 효과 확인 |

## 라이브·데이터 기획

| 관찰할 증거 | 판단 예시 | 다음 보완 행동 |
|---|---|---|
| 지표의 분모·분자·기간·집단·이벤트 정의, 데이터 출처 | ‘리텐션 상승’만으로 어느 집단의 어떤 변화인지 판단하기 어려움 | 지표 정의와 비교 기준을 붙이고 실측·공개 자료·가상 데이터 여부 명시 |
| 관찰→가설→대안→검증의 연결, 다른 설명 가능성 | 이벤트와 매출이 함께 올랐다는 사실은 이벤트의 인과 효과를 확정하지 않음 | 신규 유입·시즌·다른 패치 등 대안 원인과 비교·검증 방법 추가 |
| 이벤트 대상·보상·일정·운영 제약, 악용·장애 대응과 종료 기준 | 이벤트 아이디어는 확인되지만 운영 실행·수익 성과까지 확인되지는 않음 | 목적에 맞는 모니터링 지표, 이상 신호와 대응·중단 조건을 설계 |
| 본인이 관여한 판단·변경, 적용 전후와 잔여 문제 | 팀 KPI와 개인 기여는 분리해야 하며 계획은 실행 결과가 아님 | 담당한 의사결정과 관찰 결과를 연결; 학습 작업은 분석 한계·후속 검증으로 보완 |

## UX·내러티브 기획 — 해당 공고에 필요할 때

| 세부 직무 | 관찰할 증거와 판단 예시 | 다음 보완 행동 |
|---|---|---|
| UX | 실제 확인한 화면 흐름·상태·정보 위계와 사용 과제. 화면이 정돈돼 보여도 과제 성공·오조작 감소는 검증 필요 | 핵심 과제 하나의 시작→완료와 오류·빈 상태·취소 흐름을 잇고 관찰한 사용 문제를 보충 |
| 내러티브 | 플레이 행동과 서사 전달의 연결, 분기 조건·변수·합류, 대사 제약. 세계관 분량만으로 게임 내 전달·분기 설계를 입증하지 못함 | 대표 퀘스트의 선택→상태 변화→결과와 누락·충돌 방지 규칙을 작성 |

역기획은 화면·플레이에서 관찰한 동작과 내부 구현·설계 의도에 대한 추정을 구분한다. 재현 가능한 관찰과 대안 해석이 있는지 본다. 내부 수치나 개발자의 의도를 확정하지 않으며, 분석한 게임의 출시·운영 실적을 지원자 실적으로 쓰지 않는다.

## 개발·아트·QA

| 직무 | 관찰할 증거와 판단 예시 | 다음 보완 행동 |
|---|---|---|
| 개발: 구현·구조 | 본인 기능, 문제·제약, 코드/구조 선택과 대안. 언어·엔진 목록은 사용 진술이며 설계 역량 전체를 입증하지 않음 | 관련 기능의 본인 범위와 구조 선택 하나를 코드 위치·설계 설명에 연결 |
| 개발: 성능·안정성 | 재현 조건·측정 환경, 로그/프로파일, 수정·검증. 최적화율만으로 비교의 공정성이나 재발 방지를 확인할 수 없음 | 동일 조건의 전후 측정과 수정 원인·회귀 확인 범위를 보충 |
| 아트: 표현·제작 | 해당 세부 직무의 실제 이미지·영상, 목표 스타일·제약, 시안→피드백→수정과 본인 기여 | 목표와 선택 이유를 대표 결과물에 붙이고 공동·외부 소스·생성 도구의 사용 범위 명시 |
| 아트: 게임 적용 | 공고에 필요할 때 엔진 적용 화면, 규격·예산, 리깅·애니메이션·최적화 등 해당 파이프라인 증거 | 렌더 이미지뿐이라면 적용 역량은 유보하고 관련 규격·적용 결과·수정 사례 보충 |
| QA: 설계·재현 | 기능/위험별 범위, 테스트 케이스, 환경·절차·기대/실제 결과, 심각도·우선순위 이유 | 버그 목록만 있으면 재현성과 판단을 유보하고 대표 건의 재현 절차·영향을 완성 |
| QA: 추적·검증 | 수정 확인·회귀 범위, 로그·협업, 공고에 필요할 때 자동화. 발견 건수만으로 품질 기여를 판단하지 않음 | 수정 전후와 관련 기능 재검증을 연결하고 남은 위험·미검증 범위를 명시 |

코드·실행물을 읽지 않았다면 코드 품질·안정성을, 이미지·영상·실행 화면을 보지 않았다면 시각 품질·동작을 평가하지 않는다. 텍스트 설명만 확인한 경우 해당 설명에 대한 판단으로 범위를 한정한다.
