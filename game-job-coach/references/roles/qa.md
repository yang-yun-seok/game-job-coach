# QA 세부 직무 코칭 기준

이 문서는 테스트 경험과 자료를 읽기 위한 **코칭 제안 기준**이다. 업계 공통 합격선이나 모든 지원자에게 요구할 산출물 목록이 아니다.
공고의 제품·테스트 대상·필수·우대·경력 수준을 우선한다. 자동화·성능·현지화 등 공고에 없는 전문 범위를 필수 조건으로 추가하지 않는다.
QA라는 이름이 같아도 실제 책임이 다르므로 기능 검증, 테스트 도구 개발, 플랫폼 확인, 언어 검증 중 어느 업무인지 먼저 구분한다.

## 공통 관찰 원칙

- 신입은 학습·개인·팀 프로젝트의 테스트 설계와 재현·수정 확인을 해당 범위에서 인정한다. 상용 출시·대규모 이용자·전체 플랫폼 검증을 일괄 요구하지 않는다.
- 경력은 담당 기능·플랫폼·기간, 테스트 결정권, 협업 범위, 출시 판단에 제공한 정보와 검증 결과를 확인한다. 팀의 품질 성과를 본인 성과로 합치지 않는다.
- 자료에 없는 경험은 ‘자료에서 확인 불가’로 남긴다. 결함 발견 수, 테스트 케이스 수, 자동화율만으로 기여나 역량의 높고 낮음을 결정하지 않는다.
- 실행 화면·재현 기록·로그를 보지 않았다면 실제 결함 원인이나 수정 성공을 확인했다고 하지 않는다. 코드 미열람 상태에서 테스트 코드 품질도 단정하지 않는다.
- 테스트 의도, 실행 기록, 관찰 결과, 원인 가설, 개발팀이 확인한 원인, 수정 재검증을 구분한다. 로그에 같은 시각의 오류가 있다는 것만으로 원인을 확정하지 않는다.
- 기밀 빌드·계정·내부 이슈를 요구하지 않는다. 익명화한 티켓, 축약한 테스트 시나리오와 가상 데이터 재현을 허용하고 실제 환경과 다른 점을 표시한다.
- 성능 수치에는 기기·실행 환경·빌드·설정·측정 지표·부하·반복 방식·비교 구간이 필요하다. 다른 조건의 측정값으로 개선율을 만들지 않는다.
- 아래 ‘보완 완료’는 선택한 과제를 끝내는 기준이다. 체크리스트의 모든 항목이 채워져야 지원 가능하다는 뜻이 아니다.

## 기능·콘텐츠 QA

**실제 담당 일:** 기능과 콘텐츠의 의도·규칙을 읽고, 사용자 흐름·상태·데이터·예외를 테스트하며 결함 재현과 수정 확인, 관련 영역의 회귀 검증을 수행한다.

**확인할 산출물:** 기능/위험별 테스트 범위, 대표 케이스, 탐색 테스트 메모, 재현 티켓, 기대/실제 결과, 수정 확인과 남은 미검증 범위.

- 좋은 근거: 퀘스트 보상 수령의 선행 상태, 수행 절차, 기대/실제 결과를 제시하고 재접속·중복 입력 등 관련 위험을 고른 이유를 설명한다.
- 부족한 근거: 버그 제목과 스크린샷만 있다. 발견 경험은 보이지만 발생 조건·재현성·영향과 수정 여부는 확인하기 어렵다.
- 설계 판단: 정상 경로 개수보다 상태 변화·경계값·취소·실패·복귀에서 무엇이 달라지는지 확인한다. 모든 기능에 같은 테스트 조합을 강요하지 않는다.
- 기대 결과 판단: 기획 문서, 승인된 동작, 비교 기준의 출처를 확인한다. 명세가 모호한 경우 결함으로 단정하기 전에 질문·합의한 과정을 본다.
- 우선순위 판단: 이용자 영향·발생 범위·재현 빈도·회피 가능성·일정 조건을 연결한다. 심각도와 수정 순서를 같은 의미로 취급하지 않는다.
- 신입 보완: 공개적으로 사용할 수 있는 게임·개인 프로젝트의 기능 한 개를 선정해 재현 가능한 기록을 만들 수 있다. 내부 명세가 없으면 관찰과 기대 가정을 분리한다.
- 경력 확인: 맡은 기능 범위와 일정 제약, 개발·기획과의 쟁점, 수정 후 관련 기능을 어디까지 다시 확인했는지 본다.

**보완 완료:** 대표 사례 하나에 환경·선행 상태·절차·기대/실제·영향 근거가 있으며, 실행한 수정 확인/회귀와 미실행 범위를 구분한다.

**면접 핵심 질문:** “시간이 절반으로 줄면 무엇을 먼저 확인하나요?”, “기대 동작이 불명확할 때 어떻게 결정했나요?”, “수정된 기능 외에 어떤 영역을 왜 다시 확인했나요?”

**평가 경계:** 개발자가 수정했다는 진술만으로 재검증 완료로 처리하지 않는다. 발견하지 못한 결함이 있었다는 사실만으로 테스트 설계 전체를 실패로 단정하지 않는다.

## 기술·자동화 QA

**실제 담당 일:** 반복 확인을 코드·도구로 실행하고, 테스트 데이터와 실행 환경을 관리하며 실패 원인·불안정 테스트·결과 추적을 다룬다.

**확인할 산출물:** 자동화 대상을 고른 이유, 입력/기대값/판정 조건, 코드 또는 축약 예제, 실행·결과 기록, 데이터 초기화와 실패 진단·유지보수 사례.

- 좋은 근거: 동일 보상 요청의 결과를 상태와 데이터로 판정하고, 테스트 전후 상태를 정리하며 실패 시 남길 정보를 설계한다.
- 부족한 근거: 자동 클릭 영상이나 도구명만 있다. 조작 자동화는 보이지만 성공/실패 판정, 재실행 독립성, 회귀 탐지 능력은 확인되지 않는다.
- 대상 선정 판단: 반복 빈도·판정 가능성·변경 비용·실행 시간을 실제 과제와 연결한다. 수동 테스트를 모두 자동화하는 것을 목표로 강요하지 않는다.
- 결과 판단: 제품 결함, 테스트 코드 오류, 데이터 오염, 환경 문제를 어떻게 나눴는지 본다. 실패 횟수를 제품 결함 수로 바로 바꾸지 않는다.
- 안정성 판단: 임의 대기나 반복 재시도로 실패를 가렸는지, 상태 준비·정리·시간 제한과 진단 정보가 있는지 확인한 코드 범위에서 판단한다.
- 신입 보완: 작은 기능의 자동 검증과 명확한 실패 사례만으로도 학습 증거가 된다. 조직 전체 테스트 프레임워크나 CI 운영 경험을 요구하지 않는다.
- 경력 확인: 개발·유지보수한 범위, 팀이 결과를 사용하는 방식, 변경 후 신뢰성 확인과 실행 비용에 대한 본인 판단을 확인한다.

**보완 완료:** 선택한 테스트에 준비→실행→판정→정리 흐름과 실패 사례가 있고, 실제 실행 결과와 알려진 제한을 설명할 수 있다.

**면접 핵심 질문:** “왜 이 항목을 자동화했나요?”, “테스트 통과가 어떤 품질을 보장하고 무엇은 보장하지 않나요?”, “간헐적으로 실패할 때 제품과 테스트 중 어느 쪽인지 어떻게 좁혔나요?”

**평가 경계:** 자동화율의 분모와 대상 범위가 없으면 비율을 비교하지 않는다. 자동화 코드가 있다는 사실만으로 유지보수성·실행 안정성·테스트 효과를 확정하지 않는다.

## 호환성·성능·플랫폼 QA

**실제 담당 일:** 기기·환경·입력·설정·플랫폼 동작 차이와 자원 제약을 검증하고, 재현 조건을 좁혀 기능·성능·중단/복귀 문제를 보고한다.

**확인할 산출물:** 환경 선택 근거와 테스트 매트릭스, 장면·계정 상태·설정, 측정 기록, 기기별 재현 비교, 중단/복귀 시나리오, 수정 후 동일 조건 재검증.

- 좋은 근거: 같은 장면·이동 경로·화질 설정에서 기기별 프레임 시간이나 메모리를 기록하고, 반복 실행·발열·장시간 사용 조건을 구분한다.
- 부족한 근거: ‘저사양에서 느림’이나 단일 FPS 캡처만 있다. 증상 진술로 인정하되 비교 조건·지속성·영향 범위·원인은 유보한다.
- 호환성 판단: 접근 가능한 모든 기기를 나열하기보다 대상 환경과 위험을 기준으로 조합을 선정했는지 본다. 확인하지 않은 기기의 호환성을 일반화하지 않는다.
- 성능 판단: 평균값 외 지표는 공고·문제에 필요할 때 제안한다. 수치의 단위와 관찰 구간이 없는 ‘최적화 완료’ 표현은 사실 확인 대상으로 남긴다.
- 플랫폼 판단: 로그인/연결 변화, 저장·복귀, 입력 장치 변경 등 공고에 관련된 동작과 확인 근거를 본다. 읽지 않은 플랫폼 심사 기준을 알고 있는 것처럼 말하지 않는다.
- 신입 보완: 보유 기기나 명시한 실험 환경 내 비교도 인정한다. 실제 기기와 에뮬레이션 결과를 구분하고 장비 부족 자체를 역량 부족으로 보지 않는다.
- 경력 확인: 환경 선정과 일정 조정, 재현 범위 축소, 개발팀 전달 및 수정 재측정에서 맡은 책임을 확인한다.

**보완 완료:** 문제 하나의 환경·입력·장면·측정/관찰 방식·반복 결과가 남아 있고, 비교 조건과 확인하지 못한 조합을 분명하게 제시한다.

**면접 핵심 질문:** “기기가 제한되면 어떤 조합을 고르나요?”, “측정값 차이가 제품 변경 때문이라고 어떻게 확인하나요?”, “간헐적인 멈춤의 재현 범위를 어떻게 줄였나요?”

**평가 경계:** 성능 QA의 관찰을 엔진 병목 원인 분석 완료로 바꾸지 않는다. 한 기기에서 재현되지 않았다는 결과는 전체 플랫폼 문제 해소를 뜻하지 않는다.

## LQA와의 경계

**실제 담당 일:** 언어·지역 설정에서 문자열과 UI·문맥·표시 상태를 확인하고, 언어 판단이 필요한 문제를 현지화 담당자와 연결한다. 채용 공고에 따라 언어 검수와 기능 검수가 함께 포함될 수 있다.

**확인할 산출물:** 언어/지역별 재현 티켓, 화면·문자열 식별 정보, 문맥과 기대 근거, 용어/스타일 자료 적용 사례, 수정 후 표시와 기능 재검증.

- 좋은 근거: 특정 언어의 긴 문자열이 버튼을 가려 진행을 막는 상황을 해상도·화면 상태와 함께 기록하고, 수정 후 다른 상태에서도 표시를 확인한다.
- 부족한 근거: ‘번역이 어색함’이나 언어 능력만 있다. 의견 또는 언어 경험으로 인정하되 실제 LQA의 문맥 판단·보고·재검증 근거는 별도 확인한다.
- QA에서 볼 범위: 잘림·겹침·누락·문자 깨짐·언어 전환 후 상태·지역별 형식의 표시와 기능 영향, 재현성과 보고의 명확성.
- 언어 전문 검토 범위: 의미 정확성·어조·용어·문화적 맥락·원문 의도. 해당 언어와 맥락을 확인하지 못했다면 오역이나 적절성을 확정하지 않는다.
- 연결 기준: 번역 품질·용어 관리·현지화 제작 과정이 주 업무라면 [현지화 직무 지침](localization.md)과 함께 평가한다. QA 공고라는 이유로 번역·프로젝트 관리 역량까지 자동으로 필수화하지 않는다.
- 신입 보완: 접근 가능한 화면과 공개 문맥의 사례를 사용하고 제안 문구의 이유를 밝힌다. 번역안을 승인된 정답처럼 쓰거나 전문 언어 감수를 했다고 꾸미지 않는다.
- 경력 확인: 언어별 검수와 기능 검수 중 맡은 범위, 언어 담당자와 쟁점을 합의한 과정, 수정 적용과 회귀 확인을 구분한다.

**보완 완료:** 사례 하나에 언어·화면/문맥·재현·영향·기대 근거가 연결되고, 직접 판단한 범위와 전문 언어 확인이 필요한 범위가 분리된다.

**면접 핵심 질문:** “언어 문제와 UI 구현 문제를 어떻게 구분했나요?”, “문맥이 부족한 문자열은 어떻게 확인했나요?”, “문구 변경 뒤 어떤 기능과 화면을 다시 봤나요?”

**평가 경계:** 외국어 시험 점수만으로 LQA 역량을 확정하지 않는다. 읽지 않은 원문·화면·용어집을 근거로 번역 품질을 평가하지 않는다.

## 대표 사례를 검토하는 순서

1. **범위:** 무엇을 검증해야 했고, 어떤 조건·시간·환경 때문에 범위를 골랐는지 확인한다. 학습 작업의 가정과 실제 업무 요청을 구분한다.
2. **설계:** 기대 결과의 근거, 주요 상태·위험, 제외한 항목과 이유를 읽는다. 문서 양이나 케이스 수로 완전성을 판단하지 않는다.
3. **실행:** 환경·선행 조건·절차·관찰 기록이 맞물리는지 본다. 실행하지 않은 케이스는 계획으로, 실제 실행은 결과와 연결한다.
4. **전달:** 증상과 영향이 재현 가능한 형태로 전달됐는지, 원인 추정이 관찰 사실과 구분되는지 확인한다.
5. **재검증:** 수정 확인·회귀·보류·미검증을 나누고, ‘완료’가 뜻하는 조건을 확인한다. 출시 결정 전체를 QA 개인의 결정으로 추정하지 않는다.

## 보완 과제와 면접 피드백

- 버그 보고서가 약하면 새 결함을 대량 탐색하게 하기 전에 기존 대표 건의 재현 조건과 기대/실제 결과를 보완한다.
- 테스트 설계가 약하면 기존 기능의 중요한 상태와 위험을 연결하고, 왜 먼저 확인할지 설명하게 한다. 모든 조합을 전수 작성하도록 요구하지 않는다.
- 수정 확인이 없으면 실제 실행 가능 여부를 먼저 본다. 실행할 수 없을 때는 재검증 계획을 제시하되 확인 완료로 포장하지 않는다.
- 가상 피드백 예: “포트폴리오의 상점 결함은 재현 절차가 있지만 구매 전 잔액과 연결 상태가 없습니다. 이 조건을 보충하고 같은 상태로 재현되었는지 구분해 주세요.” 지원자 사실로 재사용하지 않는다.
- 면접 답변은 선택 이유·관찰·전달·후속 확인을 연결해 본다. 개발 원인을 즉석에서 맞히는 능력이나 도구 이름 암기를 QA 역량 전체로 평가하지 않는다.
- 요청 범위에서 최대 3개 행동에 대상 자료·수정 위치·완료 기준을 붙인다. 문장 수정과 새 실험, 사실 확인이 각각 필요한지 분리해 제안한다.
