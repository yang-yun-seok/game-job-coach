# 개발 세부 직무 코칭 기준

이 문서는 작업물에서 무엇을 확인하고 어떻게 보완할지 정하는 **코칭 제안 기준**이다. 회사의 공식 평가표나 모든 지원자의 제출물 목록이 아니다.
공고의 담당 업무·필수·우대와 경력 수준을 먼저 읽고, 관련된 세부 직무와 증거만 골라 쓴다. 공고에 없는 상용 규모·기술·운영 경험을 필수 요건으로 추가하지 않는다.
여러 업무가 섞인 공고는 실제 책임의 비중으로 읽는다. ‘클라이언트 개발자’라는 명칭만으로 렌더링·네트워크·빌드를 모두 평가하지 않는다.

## 자료를 읽는 공통 규칙

- 신입의 학습·개인·팀 프로젝트도 구현한 범위 안에서 인정한다. 작은 기능의 선택 이유와 검증은 유효한 근거이며 대규모 상용 서비스 경험을 일괄 요구하지 않는다.
- 경력은 본인의 결정권·담당 기간·협업 경계·검증 결과를 확인한다. 팀의 출시나 성능 개선 전체를 개인 성과로 옮기지 않는다.
- 공고가 언어·자료구조·알고리즘·OS·동시성 등 기초 역량을 요구하면, 해당 지식이 실제 구현 선택과 연결되는 설명을 확인한다. 기술 목록이나 프로젝트 존재만으로 숙련도를 판정하지 않는다.
- `자료 위치 → 확인한 구현/설명 → 판단 가능한 범위 → 남은 확인점`으로 기록한다. 코드를 읽지 않았다면 코드 품질, 실행물을 보지 않았다면 실제 동작을 판정하지 않는다.
- 로그·프로파일을 읽지 않았다면 원인이나 성능 수치를 검증했다고 하지 않는다. 서술만 있을 때는 ‘지원자가 제시한 결과’로 한정한다.
- 성능 수치는 하드웨어·실행 환경·빌드 조건·입력 부하·측정 지표·반복 방식·비교 구간을 함께 본다. 조건이 다르면 개선율을 직접 비교하지 않는다.
- 기밀 코드·내부 로그·보안 설정을 요구하지 않는다. 익명화한 구조도, 축약 코드, 가상 데이터로 재현한 실험과 본인 설명을 허용하고 실제 자료와의 차이를 표시한다.
- 아래 ‘보완 완료’는 선택한 보완 과제의 종료 기준이다. 모든 항목의 추가 제출을 요구하거나 자료 부재를 바로 역량 부족으로 바꾸지 않는다.

## 클라이언트·게임플레이

**실제 담당 일:** 입력을 캐릭터·전투·UI·카메라·게임 상태 변화로 연결하고, 콘텐츠 데이터와 표현 계층을 연동하며 기능 변경과 오류를 다룬다.

**확인할 산출물:** 본인이 구현한 플레이 구간, 상태 전이/객체 수명 설명, 관련 코드 위치, 입력·데이터·이벤트 흐름, 재현 절차와 수정 기록 중 해당 기능을 설명하는 자료.

- 좋은 근거: 스킬 시전 중 피격·취소·재입력의 우선순위를 정의하고, 실제 구현의 상태 전환과 재현 결과를 연결한다.
- 부족한 근거: ‘전투 시스템 구현’과 엔진 이름만 있다. 구현 경험 진술은 인정하되 본인 범위·예외 처리·구조 선택은 확인 불가로 남긴다.
- 구조 판단: 기능 규모와 변경 요구에 비춰 선택 이유를 읽는다. 특정 패턴을 썼다는 이유만으로 좋은 설계라고 하지 않는다.
- 신입 보완: 하나의 상호작용에서 정상 흐름과 실제 발생한 예외를 설명하면 된다. 모든 장르 시스템이나 완제품 분량을 요구하지 않는다.
- 경력 확인: 기존 기능과의 연결, 다른 직군의 요청 수용, 수정 영향과 본인이 맡은 회귀 확인 범위를 분리한다.

**보완 완료:** 대표 기능 하나에 본인 담당, 입력→상태→결과, 선택한 구조의 이유, 예외 한 사례와 실제 확인 결과가 연결된다. 미실행 확인은 계획으로 표시한다.

**면접 핵심 질문:** “이 상태를 별도 관리한 이유는 무엇인가요?”, “취소와 완료가 같은 시점에 발생하면 어떻게 처리했나요?”, “변경 후 어떤 플레이가 깨질 수 있어 확인했나요?”

**평가 경계:** 영상의 자연스러운 동작만으로 코드 구조·메모리 안전성·재현되지 않은 상황의 안정성을 확정하지 않는다.

## 서버·네트워크

**실제 담당 일:** 세션·매치·게임 상태와 저장 데이터를 다루고, 요청 순서·동시 처리·권한·재시도·연결 종료에 따른 일관성을 설계하고 확인한다.

**확인할 산출물:** 요청/응답과 상태 흐름, 데이터 변경 경계, 동시성 처리 설명, 본인 코드 또는 축약 예제, 오류·부하 실험 조건과 결과.

- 좋은 근거: 보상 수령 요청이 중복되거나 저장 도중 실패하는 경우를 정의하고, 재시도 시 결과와 검증 방법을 설명한다.
- 부족한 근거: ‘동접 N명 처리’만 있고 접속 유지·실제 요청·봇 행동의 구분이 없다. 해당 수치는 부하 대응 능력 전체의 증거로 쓰지 않는다.
- 네트워크 판단: 동기화 대상, 권위가 있는 상태, 지연·순서 변경·연결 복구가 플레이에 미치는 영향을 실제 구현 범위에서 확인한다.
- 신입 보완: 로컬 환경의 두 클라이언트나 제한된 부하 실험도 인정한다. 배포 규모를 키우기보다 실패 조건과 관찰의 일치를 먼저 본다.
- 경력 확인: 맡은 서비스·데이터·인터페이스 경계, 장애 시 의사결정, 다른 서비스와의 계약 변경 및 검증 범위를 구분한다.

**보완 완료:** 대표 요청 하나의 정상·중복·실패 흐름과 데이터 결과를 추적할 수 있고, 실행한 검증의 입력·관찰·한계를 설명한다.

**면접 핵심 질문:** “동일 요청이 두 번 오면 어떤 상태가 남나요?”, “응답 전에 연결이 끊기면 클라이언트는 무엇을 믿어야 하나요?”, “측정에서 먼저 한계에 도달한 자원은 무엇이었나요?”

**평가 경계:** 특정 서버 구조나 데이터베이스 사용을 보편적 정답으로 삼지 않는다. 부하 실험 결과를 실제 이용자 규모나 장기 운영 성과로 확대하지 않는다.

## 엔진·렌더링

**실제 담당 일:** 프레임 처리·렌더링 경로·자원 관리 등 기반 기능을 구현하거나 수정하고, 화면 품질과 CPU/GPU·메모리 비용 사이의 선택을 검증한다.

**확인할 산출물:** 본인이 바꾼 처리 단계, 렌더 결과와 비교 이미지, 관련 코드/셰이더, 캡처·프로파일 자료, 테스트 장면과 성능 측정 조건.

- 좋은 근거: 같은 장면·해상도·카메라에서 병목 구간을 관찰하고, 변경한 패스의 비용과 시각적 손실을 함께 비교한다.
- 부족한 근거: 고품질 화면과 ‘FPS 향상’만 있다. 표현 결과와 개선 주장은 보이지만 병목 원인·기여·비교 조건은 확인되지 않는다.
- 기술 판단: 수학식·알고리즘 설명을 실제 데이터 흐름, 정밀도·메모리·동기화 제약과 연결한다. 용어의 개수로 깊이를 판정하지 않는다.
- 신입 보완: 작은 렌더러·셰이더·자원 관리 실험의 재현성과 한계를 인정한다. 상용 엔진 전체를 이해하거나 수정했을 것을 요구하지 않는다.
- 경력 확인: 엔진 공통 기능에 미친 영향, 플랫폼 차이, 기존 콘텐츠 호환성과 팀 적용 과정에서 본인이 책임진 부분을 확인한다.

**보완 완료:** 선택한 문제에 대해 변경 위치, 동일 조건의 결과, 성능/품질의 교환 관계와 남은 한계를 제시한다. 성능 자료가 없으면 구현 설명의 보완으로 범위를 좁힌다.

**면접 핵심 질문:** “CPU와 GPU 중 어느 구간이 원인이라고 판단했나요?”, “품질을 유지했는지 어떤 장면에서 비교했나요?”, “입력 크기나 자원 수가 커지면 비용이 어떻게 달라지나요?”

**평가 경계:** 화면만 보고 렌더링 기법이나 최적화 원인을 단정하지 않는다. 평균 FPS만으로 순간 지연·메모리 사용·전체 프레임 안정성을 대신 평가하지 않는다.

## 툴·빌드

**실제 담당 일:** 제작자의 반복 작업과 오류를 줄이는 에디터·검증 도구를 만들고, 자산 처리·빌드·배포 준비 과정의 재현성과 실패 진단을 개선한다.

**확인할 산출물:** 기존/변경 작업 흐름, 사용자와 입력·출력 정의, 도구 화면·실행 예제, 잘못된 입력 처리, 빌드 단계·산출물·실패 기록과 복구 설명.

- 좋은 근거: 데이터 검증 도구가 어떤 오류를 어느 단계에서 잡는지 예시를 제공하고, 사용자가 수정 위치를 찾아 재실행하는 흐름을 보여준다.
- 부족한 근거: 도구 화면이나 ‘작업 시간 단축’만 있다. 사용 사실과 편의성 주장은 보이지만 적용 범위·사용자 반응·시간 측정은 별도 확인한다.
- 빌드 판단: 같은 입력에서 결과를 추적할 수 있는지, 실패 단계를 식별하고 다시 실행할 수 있는지 본다. 도구 종류가 많다는 사실을 자동화 품질로 바꾸지 않는다.
- 신입 보완: 본인이나 팀원의 반복 작업 하나를 해결한 스크립트도 인정한다. 사용자의 문제와 오류 처리까지 설명하면 범위에 맞는 근거가 된다.
- 경력 확인: 도입·유지보수 책임, 제작팀의 피드백, 기존 파이프라인 연결, 실패가 작업 일정에 미친 영향과 본인 대응을 확인한다.

**보완 완료:** 하나의 실제 작업에서 사용 전후 단계, 정상·오류 입력의 결과, 실패 시 수정/재실행 방법이 설명된다. 시간 절감 수치는 작업량·환경·측정 구간을 함께 제시한다.

**면접 핵심 질문:** “누가 어떤 작업에서 막혀 만들었나요?”, “도구가 틀린 결과를 조용히 내지 않도록 무엇을 확인했나요?”, “빌드 실패의 원인과 재실행 단위를 어떻게 찾나요?”

**평가 경계:** 도구 사용 건수나 스크립트 줄 수를 생산성의 대용 지표로 삼지 않는다. 제안한 자동화와 실제 적용한 자동화를 구분한다.

## 인프라·SRE

**실제 담당 일:** 서비스 실행 환경·배포·관측·장애 대응을 다루고, 가용성·성능·운영 비용과 변경 위험 사이의 판단을 지원한다.

**확인할 산출물:** 익명화한 구성도, 배포/롤백 흐름, 지표·알림의 목적, 장애 대응 타임라인, 복구·부하 실험의 조건과 결과, 본인 운영 범위.

- 좋은 근거: 특정 실패 신호를 어떤 지표로 감지하고 어떤 조치를 했는지 연결하며, 복구 확인과 남은 위험을 구분한다.
- 부족한 근거: 클라우드 서비스 목록이나 ‘무중단 구축’만 있다. 구성 경험은 인정하되 실제 전환 중 요청 손실·중복·관찰 범위는 확인 불가로 남긴다.
- 운영 판단: 알림 수보다 신호가 조치로 이어지는지, 배포 실패를 발견하고 되돌릴 수 있는지, 변경 전후의 확인 범위를 본다.
- 신입 보완: 개인 서비스의 배포·모니터링·장애 재현도 학습 증거다. 온콜 경험이나 상용 트래픽을 필수로 붙이지 않는다.
- 경력 확인: 직접 운영한 구성 요소, 장애 중 맡은 판단·실행·공유, 재발 방지 적용과 검증 결과를 팀 전체 대응과 분리한다.

**보완 완료:** 대표 실패 하나의 감지→판단→조치→복구 확인이 이어지고, 실험/실제 사고의 구분과 본인 책임 범위가 명확하다.

**면접 핵심 질문:** “이 알림이 울리면 첫 판단은 무엇인가요?”, “롤백해도 되돌아가지 않는 상태가 있나요?”, “복구했다고 판단한 관찰과 남은 위험은 무엇이었나요?”

**평가 경계:** 구성도만으로 가용성을 보장하지 않는다. 비용·처리량·복구 시간은 환경·워크로드·관찰 기간과 비교 구간이 있을 때만 해석한다.

## 보안·안티치트

**실제 담당 일:** 신뢰 경계와 공격·오용 가능성을 파악하고, 검증·탐지·대응 절차를 설계하며 오탐과 플레이 영향을 함께 확인한다.

**확인할 산출물:** 허가된 실험 환경의 위협 모델, 입력/권한 검증 설계, 익명화한 탐지 사례, 정상/이상 행동 구분 방법, 대응 및 재검증 설명.

- 좋은 근거: 클라이언트가 보내는 값을 어디까지 신뢰하는지 정하고, 정상 동작과 조작된 입력을 비교해 방어의 적용 범위와 우회 한계를 설명한다.
- 부족한 근거: ‘핵 차단’이나 탐지 건수만 있다. 무엇을 어떤 조건에서 탐지했는지, 정상 이용자의 오탐과 탐지 누락을 어떻게 봤는지 확인되지 않는다.
- 판단 초점: 취약점 이름보다 원인·재현 조건·영향·방어·잔여 위험의 연결을 본다. 기밀 탐지 규칙이나 실제 공격 가능한 세부 정보를 제출하게 하지 않는다.
- 신입 보완: 본인이 소유하거나 사용 허가를 받은 작은 실습 환경의 재현·방어 비교를 인정한다. 실제 이용자를 대상으로 한 탐지 운영을 요구하지 않는다.
- 경력 확인: 분석·탐지 구현·대응 운영 중 맡은 범위, 다른 팀과의 판단 경계, 오탐 처리와 수정 검증을 확인한다.

**보완 완료:** 하나의 위협에 대해 신뢰 경계, 발생 조건, 방어의 이유, 정상 동작 영향과 검증 한계를 설명한다. 공개가 어려우면 비식별 사례와 축약 모델로 대체한다.

**면접 핵심 질문:** “어떤 입력을 신뢰하지 않았고 이유는 무엇인가요?”, “정상 플레이와 구분하기 어려운 경우를 어떻게 다뤘나요?”, “방어 이후에도 남는 위험은 무엇인가요?”

**평가 경계:** 실습의 성공을 상용 보안 수준으로 확대하지 않는다. 발견 건수·차단율만으로 품질을 판정하거나 공개 자료 부재를 경력 부재로 단정하지 않는다.

## 피드백을 작성할 때

- ‘기술 스택을 더 늘리세요’ 대신 공고에 필요한 기능·문제 하나와 기존 근거를 연결한다. 새 프로젝트 제안 전 이미 한 작업의 설명·검증을 보완할 수 있는지 확인한다.
- 예: “서버 포트폴리오의 보상 수령 설명에는 저장 실패 후 처리 결과가 없습니다. 기존 구현의 재시도 결과를 추가하면 데이터 일관성 판단 범위가 분명해집니다.” 이는 문장 작성 예시이며 지원자 사실이 아니다.
- 코드 검토를 수행했다면 읽은 파일·함수와 조건을 기록하고, 실행하지 않았다면 실행 검증과 구분한다. 일부 코드 확인을 프로젝트 전체 평가로 넓히지 않는다.
- 최종 행동은 요청 범위에서 최대 3개로 정하고, 문서 보충·기존 사실 확인·새 검증 실행 중 무엇이 필요한지와 완료 기준을 붙인다.
