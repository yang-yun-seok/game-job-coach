# 오디오 직무의 근거를 읽는 관점

회사 공고의 담당 업무·제작 단계·경력 수준을 먼저 확인한다. 아래는 코칭용 제안 기준이며 회사의 공식 채용 기준이나 공통 합격컷이 아니다.
사운드 디자인, 작곡, 오디오 구현, 음성 제작은 같은 데모에서도 확인해야 할 책임과 증거가 다르다. 공고가 요구하지 않은 역할까지 일괄 평가하지 않는다.
장르·음악 스타일·엔진·미들웨어·녹음 장비·언어·납품 규격은 공고나 실제 프로젝트의 조건을 따른다. 임의의 필수 툴·러닝타임·트랙 수를 만들지 않는다.
개인 사운드 리디자인·작곡·게임잼·학습 구현도 적절한 근거다. 본인의 제작과 검증 범위 안에서 평가하고 상용 납품·출시 크레딧·라이브 성과로 바꾸지 않는다.

## 공통 확인과 관찰 한계

- `자료 위치·타임코드 → 실제 청취·관찰 → 본인 기여 → 선택·검증 → 한계` 순서로 판단을 연결한다.
- 음원을 직접 듣지 못하면 음색·믹스·음질·음악적 완성도 평가는 유보한다. 파형 이미지나 텍스트 설명만으로 청각적 품질을 단정하지 않는다.
- 영상 없이 음원만 들었다면 화면과의 동기·게임 상황에서의 정보 전달은 유보한다. 녹화 데모만 확인했다면 라이브 상호작용·지연·성능은 별도다.
- 재생 환경·압축·출력 레벨·파일 손상이 관찰을 제한하면 그 범위를 밝힌다. 듣기 어려운 부분을 곧바로 제작 결함으로 확정하지 않는다.
- 원작 영상·기존 음원·라이브러리·협업자 작업·생성 도구 활용과 본인 녹음·편집·작곡·구현을 구분한다. 무음화·교체 범위도 표시한다.
- 사운드 리디자인은 비공식 개인 작업이라고 밝히고, 원작 영상의 연출·음악·제작 실적을 지원자 기여로 옮기지 않는다.
- 기밀 세션·미공개 음성·권리 없는 샘플이나 대본의 공개를 강요하지 않는다. 허용된 발췌·익명화한 절차·권리가 확보된 별도 샘플로 대체할 수 있다.
- 팀 전체 크레딧만으로 모든 오디오를 맡았다고 추정하지 않는다. 담당 구간·자산·결정·협업 경계를 확인한다.

## 사운드 디자인

- 담당 결과물: 행동·피격·환경·UI 등의 사운드 자산과 공고가 정한 편집·레이어링·믹싱 작업. 구현 책임이 별도라면 구분한다.
- 관찰 증거: 실제 청취 가능한 데모, 목표 상황과 감각, 소스 출처, 원본→레이어·처리→결과, 시간에 따른 변화와 수정 기록.
- 프로젝트의 목표 스타일·레퍼런스와 톤 일관성, 기획·개발팀 피드백에 따른 수정 근거도 실제 담당 범위에서 확인한다.
- 좋은 근거: 전달해야 할 재질·거리·위험·행동을 소리 선택에 연결하고, 단독 청취와 장면 안에서의 결과를 비교할 수 있다.
- 좋은 근거: 반복 재생의 피로·변주 또는 다른 소리와의 가림 문제를 실제 조건으로 확인하고, 선택한 수정과 남은 한계를 설명한다.
- 부족한 근거: 효과음 목록이나 플러그인 나열만으로 청각적 품질을 확인할 수 없다. 큰 출력 레벨·레이어 수를 완성도와 동일시하지 않는다.
- 부족한 근거: 최종 영상만 있으면 본인 제작·라이브러리 활용·기존 음악의 기여를 분리하기 어려울 수 있다. 이를 역량 부재로 단정하지 않는다.
- 보완 행동: 대표 상황 하나에 전달 목표, 본인 소스·처리, 장면 내 결과와 실제 수정 이유를 붙인다. 새 실험은 기존 납품 과정처럼 서술하지 않는다.
- 완료 기준: 해당 구간을 직접 들을 수 있고, 본인 제작 범위와 선택 이유가 타임코드에 연결된다. 개선 주장은 비교 가능한 전후 또는 관찰 기록으로 뒷받침한다.
- 면접 질문: “이 소리에서 플레이어가 알아야 할 정보는 무엇인가요?”, “반복될 때 거슬린 요소를 어떻게 찾고 바꿨나요?”

## 작곡·적응형 음악

- 담당 결과물: 음악 테마·큐·편곡·스템과 공고에서 요구하는 루프·분기·전환 설계. 선형 작곡과 런타임 구현 책임을 구분한다.
- 관찰 증거: 실제 음악, 장면·정서·플레이 상태에 대한 의도, 테마 변형, 스템 관계, 필요 시 루프 경계·전환 규칙·실행 데모.
- 좋은 근거: 장면의 변화와 음악 구조의 선택이 연결되고, 반복·전환 시 음악적 연속성을 직접 청취할 수 있다.
- 좋은 근거: 적응형 작업에서는 상태·전환 조건·우선순위와 음악 결과를 대응시키고, 급한 상태 변화나 중단 후 재진입을 확인한 범위를 설명한다.
- 부족한 근거: 선형 음악의 완성도만으로 적응형 구현을 입증하지 않는다. 반대로 구현 데모가 없다는 이유로 작곡만 요구하는 공고를 미충족 처리하지 않는다.
- 부족한 근거: 트랙 수·장르 수가 많다는 사실만으로 목표 스타일 적합성을 판단하지 않는다. 공동 작곡·편곡·연주·샘플의 기여를 구분한다.
- 보완 행동: 목표 업무에 가까운 곡의 의도와 본인 역할을 정리한다. 적응형 업무가 필요하면 한 구간의 상태 변화와 스템·전환 결과를 연결한다.
- 완료 기준: 음악을 청취하고 의도한 구조를 구간별로 확인할 수 있다. 적응형 샘플은 실제 동작과 설계만 된 부분, 시험한 전환과 미시험 조건이 구분된다.
- 면접 질문: “반복해도 기능을 유지하도록 어떤 구조를 선택했나요?”, “전투가 갑자기 끝날 때 음악은 어떤 조건으로 넘어가나요?”

## 오디오 구현·테크니컬 오디오

- 담당 결과물: 게임 이벤트와 음원의 연결, 상태·파라미터·우선순위·공간화·믹스 동작, 자산 관리·도구·성능 개선 중 공고가 맡긴 범위.
- 관찰 증거: 이벤트와 상태 구조, 본인 설정·코드 범위, 실제 게임/테스트 장면, 오류 재현·로그, 필요 시 보이스·메모리·CPU 등의 측정 조건.
- 좋은 근거: 어떤 입력에서 어떤 소리가 시작·변경·중단되는지 실제 결과로 보여주고, 반복 트리거·중단·자산 누락 등 관련 예외를 처리한다.
- 좋은 근거: 비용이나 제작 시간 개선을 주장하면 동일 조건의 전후와 적용 범위를 제시한다. 개인 실험은 그 환경에서 확인한 결과로 한정한다.
- 부족한 근거: 미들웨어 인증·툴 이름만으로 통합·디버깅 역량을, 편집 영상만으로 이벤트 연결과 상태 처리를 확인할 수 없다.
- 부족한 근거: 음원 자체의 완성도를 구현자의 기여로 자동 평가하지 않는다. 제작자·엔진 담당자·본인의 책임과 연결 지점을 분리한다.
- 보완 행동: 대표 문제의 입력→오디오 상태→출력 흐름을 공개 가능한 형태로 설명하고, 정상 흐름과 관련 예외 하나를 직접 실행해 확인한다.
- 완료 기준: 주장한 연결을 데모 또는 허용된 실행 증거로 따라갈 수 있고, 재현 조건·수정·재확인·잔여 제약이 이어진다. 미측정 성능 개선은 주장하지 않는다.
- 면접 질문: “같은 이벤트가 연속 호출되면 어떻게 처리하나요?”, “소리가 나지 않는 문제를 어느 경계부터 확인했나요?”

## 음성 제작

- 담당 결과물: 공고에 따라 대본·발음 관리, 캐스팅 지원·연출·녹음 운영, 테이크 선정·편집·파일 정리·납품 검수. 모든 단계를 동시에 수행했다고 가정하지 않는다.
- 관찰 증거: 담당 단계, 대본/큐 식별 체계, 녹음·리테이크 판단, 발음·감정 일관성 관리, 편집 전후와 파일·버전·누락 검수 기록.
- 좋은 근거: 장면 맥락을 출연자·제작자에게 전달하고 테이크를 선택한 이유가 구체적이며, 수정 요청과 재납품 확인이 실제 역할에 연결된다.
- 좋은 근거: 편집·검수 역할은 잡음·잘림·누락·파일 매칭 등의 문제를 어떻게 찾고 확인했는지 설명한다. 제작 운영 역할은 일정·변경 대응의 근거를 본다.
- 부족한 근거: 출연자의 연기 품질만으로 지원자의 연출·운영 기여를 확인할 수 없다. 유명 출연자·참여 작품 수를 기여의 깊이로 대체하지 않는다.
- 부족한 근거: 최종 음성만으로 대본 관리·일정·검수 역량을 평가하기 어렵다. 미공개 대본이나 출연자 개인정보가 없다는 이유로 감점하지 않는다.
- 보완 행동: 허용된 사례에서 담당 단계와 문제 하나의 요청→판단→수정→확인을 정리한다. 자료 공개가 불가하면 권리가 확보된 소규모 모의 제작을 대안으로 제안한다.
- 완료 기준: 본인 책임·협업 경계가 분명하고, 식별자 또는 익명화한 예시로 수정 대상과 확인 결과를 추적할 수 있다. 모의 제작과 실제 납품 경험이 분리된다.
- 면접 질문: “리테이크가 필요한 기준을 어떻게 전달했나요?”, “대본 변경이 들어왔을 때 누락·구버전 납품을 어떻게 확인했나요?”

## 후속 피드백 적용

보완은 목표 직무에서 가장 중요한 한두 주장부터 제안한다. 녹음실·유료 툴·상용 크레딧 확보를 공통 선행 조건으로 만들지 않는다.
선택 이유가 부족하면 설명을 보충하고, 청취 자료가 없으면 품질 판단을 유보하며, 검증이 없으면 작은 검증 과제를 제안한다. 서로 다른 부족함을 한 평가로 뭉치지 않는다.
완료 판단은 보완한 구간의 새 증거를 다시 확인해서 내린다. 파일을 추가했다는 사실만으로 사운드 품질이나 구현 안정성이 개선됐다고 하지 않는다.
