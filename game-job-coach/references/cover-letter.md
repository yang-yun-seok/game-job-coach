# 자기소개서 작성·첨삭

## 작업 선택과 입력

새 작성, 기존 글 첨삭, 문항별 구조 설계, 좋은 예시·나쁜 예시 비교 중 요청한 작업을 수행한다. 사용자가 목적을 밝혔으면 선택 메뉴를 다시 제시하지 않는다. ‘자소서 도와줘’처럼 범위가 결과를 크게 바꾸는 경우 필요한 선택만 확인한다. 첨삭 요청을 새 작성으로 확대하거나, 일부 문항 요청을 전체 자소서 재작성으로 확대하지 않는다. 이전 피드백을 반영한 수정본의 비교·검증을 요청하면 [수정본 검토](revision-review.md)를 함께 읽고 반영 여부를 확인한다.

실제 기업 문항·글자 수·지원 직무를 우선한다. 회사·공고·경험이 이미 자료에 있으면 재활용한다. 자유 형식일 때만 지원 동기, 직무 관련 경험, 협업·문제 해결, 기여 방향 등의 구성을 제안한다. 네 문항이나 1·3·5년 계획을 일괄 강제하지 않는다.

지원자 경험에서 프로젝트 목적, 본인 역할, 문제, 선택한 행동과 이유, 결과, 배운 점을 확인한다. 정보가 부족하면 결과에 영향을 주는 핵심 누락만 질문하고, 이미 쓸 수 있는 문항이나 문장부터 진행한다. 모든 빈칸의 답을 받을 때까지 전체 작업을 멈추지 않는다. 확인된 부분으로 초안을 쓰고 보완 지점을 별도로 남기되, 핵심 사실이 전혀 없는 문항은 구조와 확인할 내용까지만 제시한다. 가상의 이력을 채워 완성본처럼 제시하지 않는다.

## 여러 문항의 경험 배치

여러 문항을 함께 작성·첨삭할 때는 요청받은 문항을 먼저 아래 항목으로 배치한 뒤 본문을 작업한다. 실제 문항의 표현·필수 요소·글자 수 제한을 기준으로 삼고, 문항의 평가 의도는 공개된 기준이 없는 한 해석임을 밝힌다. 사용자가 초안만 요청한 경우 배치표를 내부 작업 기준으로 사용하고 결과를 불필요하게 늘리지 않는다.

| 항목 | 배치할 내용 |
|---|---|
| 문항 | 실제 질문과 필수로 답해야 할 내용 |
| 평가 의도·요구 역량 | 이 질문으로 확인하려는 내용에 대한 해석과 연결되는 공고 요건 |
| 핵심 메시지 | 해당 답변에서 보여 줄 역량·판단을 한 문장으로 정리 |
| 경험 ID·사용할 장면 | E01 등 경험 식별자와 이번 문항에서 다룰 구체적 행동·판단 |
| 사실 근거 | 본인 역할·행동·결과의 근거 위치, 사용자 진술과 결과물 확인의 구분 |
| 분량 | 실제 제한과 계산 기준, 답변의 목표 분량·요소별 배분 |
| 진행 상태 | 지금 작성 가능한 범위와 꼭 확인해야 할 누락 |

경험 ID와 사실 근거는 [근거 기록](evidence-record.md)의 기준을 사용한다. 기존 기록이 있으면 같은 ID를 유지하고, 없으면 이번 작업에서 필요한 경험에만 ID를 붙인다. 별도 기록 파일 작성을 전제하지 않는다. 목표 분량과 실제 계산한 글자 수를 혼동하지 않는다.

- 같은 프로젝트를 여러 문항에서 재사용할 수 있다. 같은 E01이라도 직무 경험에서는 설계 대안의 선택, 협업 문항에서는 의견 차이를 조정한 행동처럼 실제로 다른 판단·장면을 다루면 된다. 문항 수에 맞추려고 하나의 경험을 별개의 프로젝트로 나누거나 새 경험을 만들지 않는다.
- 문항별로 핵심 메시지와 이를 뒷받침하는 행동이 구별되는지 확인한다. 같은 문제·행동·결과를 표현만 바꿔 반복하면 질문에 더 잘 맞는 문항에 중심 사례로 배치하고 다른 문항에서는 필요한 맥락만 짧게 사용한다. 근거가 제한적이면 그 한계를 밝히고 실제로 있는 경험 안에서 답한다.
- 초안 전체를 읽고 역할·기간·수치·프로젝트 성격이 일치하는지, 문항마다 다른 사람처럼 보이는 주장이나 상충하는 메시지가 없는지 확인한다. 직무 적합성이라는 전체 방향은 유지하되 모든 문항을 같은 결론이나 문구로 끝내지 않는다.
- 사용자가 일부 문항만 요청했다면 그 범위부터 완성한다. 다른 문항이 제공된 경우에는 중복과 사실 일관성을 확인하는 데 참고하고, 수정 범위를 임의로 넓히지 않는다.

## 작성 판단

- 문항이 확인하려는 역량과 공고의 요구를 연결하고, 가장 설명력이 좋은 실제 사례를 선택한다.
- 본인 행동·판단과 팀 결과를 구분한다. 신입의 제안서·역기획·학습용 작업은 그 성격을 유지하고, 실제 구현·출시·서비스 운영 성과로 바꾸지 않는다. 제안의 기대 효과를 측정된 결과처럼 쓰지 않는다.
- 지원 동기는 검증된 회사·프로젝트 특성과 사용자의 실제 관심·경험을 연결한다. 플레이하지 않은 게임을 플레이했다고 쓰거나, 공개되지 않은 개발 방향을 인용하지 않는다.
- 기업 자료가 없거나 확인할 수 없으면 회사·프로젝트 고유 특성에 대한 판단의 한계를 본문 밖에 밝히고, 확인된 공고의 업무·요건과 지원자 경험을 연결해 진행한다. 회사의 문화·비전·개발 방향을 상상해 지원 동기에 채우지 않는다.
- 경험형 문항에는 STAR나 SARL을 필요에 맞게 활용한다. 지원 동기나 설계 판단까지 동일 형식에 억지로 맞추지 않는다.
- 성격의 장단점은 실제 행동과 개선 루틴으로 설명한다. 지원자의 성격이나 단점을 임의로 설정하지 않는다.
- 기여 계획은 공고에서 확인한 업무와 본인이 증명한 역량에 맞춘다. 프로젝트 단계·직책·승진 시점이나 지표 개선을 근거 없이 약속하지 않는다.
- 지표가 없으면 관찰된 변화·피드백·완료 결과를 정확한 수준으로 쓴다. 보기 좋은 수치를 만들어 넣지 않는다.
- 설명은 코치의 존댓말, 자기소개서 본문은 지원자 1인칭으로 작성한다. 사용자가 요청한 문체와 기존 글의 목소리·어휘를 우선하고, 사실·논리·문항 적합성을 해치지 않는 표현은 살린다. 반복되는 수식어와 추상적인 포부를 줄이되 전문적으로 보이기 위한 획일적인 문체로 바꾸지 않는다.

## 첨삭 결과

먼저 해당 문항에서 확인하려는 내용을 짧게 설명한다. 중요한 문장에 대해 `원문 / 개선안 / 수정 이유`를 제시한다. 전체 첨삭을 요청한 경우 해당 범위의 전체 개선본을 제공하고, 문장 일부나 진단만 요청했다면 그 범위를 따른다. 구조 설계만 요청했다면 배치와 개요까지만 제공한다.

수정 이유는 문항 적합성, 사실 정확성, 본인 기여, 근거, 논리, 읽기 쉬운 표현 중 무엇이 좋아지는지 설명한다. 단순히 전문적으로 들리게 하려고 없던 업무나 도구를 추가하지 않는다.

초안의 보완 메모와 확인 필요 사실은 제출용 본문 밖에 둔다. 사실 확인이 남아 있으면 이를 최종 제출본으로 표시하지 않는다.

## 글자 수와 예시

제한이 있으면 실제 계산 도구로 세고 공백·줄바꿈 포함 기준을 밝힌다. 플랫폼의 계산 기준을 모르면 사용한 기준을 명시하고 최종 입력창에서 확인할 부분을 알린다. 지원서 입력 칸에 넣지 않는 제목·해설은 본문 글자 수와 분리한다.

좋은 예시·나쁜 예시는 같은 문항과 가능한 한 같은 경험 사실을 사용하여 구조·근거·직무 연결의 차이를 보여준다. 다른 사실을 부풀린 예시로 좋은 답변을 만들지 않는다. 가상의 교육 예시는 그렇게 표시한다. 특정 표현만으로 합격·탈락을 보장하지 않는다.
